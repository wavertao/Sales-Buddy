# P12 / P20 小Cue工作台：跨端功能变更清单

更新：2026-11-15。依据本轮P20移动原型反馈，回写P12 PC原型。本文记录产品规则及开发前差异；后续本地实现已完成，实际交付、验证与限制见[PC与移动端本地验收](小Cue工作台-PC与移动端本地验收.md)。云端版本未变。

## 范围与入口

移动端底部、PC侧栏统一为：对话、线索/商机、小Cue、目标、工具箱。小Cue使用已有虚拟形象，目标采用待办图标。小Cue首页只保留简报和Magic Cue；待办、日程归入目标，使用二级Tab切换。

现有对话历史、赢单领航员、项目概览、关键会晤赋能等能力仍需保留可达入口；本轮改导航不代表删除这些功能。工具箱承接相关已有工具入口。删除的是P20.7独立活动详情与P11跳转设计，不是删除CRM商务活动或P11能力。

## 具体规则

### 1. 八条重要事项

- 首屏查询默认pageSize=8；加载更多按相同大小继续读取，返回total与hasMore。PC双列展示，移动单列浏览，业务集合一致。
- 将AI输出校验、提示词和隔离测试中的单次生成上限从5改为8，使首次生成也能支持最多8条。不是强制每天新增8条；已有进行中事项保留并参与排序。
- 保留同一用户、项目、跟进行动的稳定身份及去重逻辑。不能因重新措辞重推已完成事项，也不能为了填满8条编造事实。
- 排序沿用优先级、AI顺序及时间规则。生成失败保留旧内容并标明上次成功时间。

### 2. 双√是可切换的状态操作

- 进行中：中性灰图标、无选中底色。点击成功后移出进行中，显示短暂撤销提示。
- 已完成：淡蓝选中态。再次点击取消完成，移回进行中；不再出现单独“恢复进行中”按钮。
- 提交中禁用重复点击，失败恢复原状态并允许重试。跨端刷新后读取同一持久化状态。
- 完成提醒不会完成CRM任务，完成CRM任务也不会自动完成Magic Cue。日报洞察闭环不等同Magic Cue状态修改。

### 3. 来源展示业务实体

- 来源项包含entityType、recordId、displayName、可用摘要/时间。线索和商机依现有项目类型/阶段规则标识，不新造CRM实体类型。
- 只显示这条提醒真正关联且用户仍有权限访问的实体；不要求每条提醒凑齐线索、商机、活动三种来源。
- 不推断原始线索与已转商机的关系；只有系统已有转换/关联记录才显示两者。原型中的三类记录仅为完整展示样例。
- 无来源、来源被撤权或删除时不得显示旧敏感摘要；保留既有授权复核和提醒可见性规则。
- 小Cue推进建议保留，固定提示为“以上为AI建议，实际的推进方案需由您判断”。移除“为什么提醒我”和原来的待核实提示块，不等于允许AI把未知写成事实。

### 4. 待办分组和统计

- 以当前执行人为本人、当前仍有权限的CRM任务为集合。经理/管理员不混入团队任务。
- 先分状态：已完成进入已完成组；取消/关闭任务不混进未完成或已完成统计。
- 未完成任务按北京时间归组：早于今天为逾期、今天为今天到期、今天之后至本周日为本周剩余事项。UI沿用“本周”标签，统计口径与该组一致，不重复计入今天。
- 晚于本周及没有截止日期的任务不能丢失；有数据时增加“以后/未排期”的折叠分组。周日的“本周”剩余数量可以为0。
- 统计先基于完整授权集合计算，不能仅统计当前页。组内按P1/P2/P3及截止时间排序，组内分页或展开加载，不用加载全部数据才能看到统计。
- “预计完成日期”映射现有dueAt，不是预计耗时。发起人读取任务创建者；历史数据缺失时显示“未记录”，不以执行人冒充发起人。
- 清单不必逐项展开AI建议；可在任务详情继续查看可用推进建议。

### 5. 日报与洞察闭环

这是新增业务能力，不能把P1.3b原型中的说明当作当前系统已实现。

- 用户主动勾选后，先完成CRM任务并写状态审计，再产生任务状态事件。AI不能代用户完成。
- 当日日报增加由taskId和完成事件关联的条目；重复请求/重试不重复写入。来源注明任务完成事件，不标成用户自然语言承诺或个人记忆。
- 只有明确的“日报洞察—待办”关联才能闭环；没有关联就只记日报。一个洞察有多个未完成任务时，全部完成后才自动闭环，不改写人工确认的状态。
- 取消完成：追加恢复事件，撤销由该次完成自动生成的闭环/日报投影；保留审计。已发布/锁定日报采用更正记录，不静默覆盖历史内容。
- 日报或洞察同步失败不撤销已经成功的CRM完成操作。显示“待办已完成，日报同步待重试”，支持后台重试，避免用户重复勾选。
- 最小新增数据：任务—洞察关联、任务状态事件、日报任务条目/投影及同步状态。当前没有日报/洞察业务对象时需先补模型和读取视图，不能只改前端文案宣称闭环成功。

### 6. 补录确认

- 文字输入可直接进入解析；语音需先授权麦克风、录音转写，再展示可编辑文本。拒绝授权或识别失败时仍可文字输入。
- 提取关联客户/项目、标题、描述、截止时间、优先级。缺失、歧义及相对日期须展示并要求用户核对，执行人固定本人。
- “补录”只生成草稿，不直接创建。确认后沿用现有草稿批准、权限校验和requestId防重复机制。
- 创建失败保留输入与草稿；未确认内容不写入CRM，不把AI补全文字当成用户已确认事实。录音留存策略应在实施时明确，默认不长期保存原始音频。

## 后续实施顺序与验收

1. 先实现导航/目标路由、八条提醒、勾选状态、实体来源与待办分组计数，复用现有CRM和会话接口。
2. 再实现语音/文字解析草稿；未接通识别能力时如实显示状态，不用固定成功样例冒充。
3. 单独补齐日报与洞察数据模型、关系和同步，再开放完成闭环；测试故障重试及取消完成。
4. PC与移动共用权限、接口及状态，分别验收布局、触控、键盘、筛选/日期返回恢复，不复制两套业务逻辑。

验收至少覆盖：不足8条与超过8条、跨日生成去重、双√完成/取消/失败、撤权来源、跨端一致；北京时间零点/周日/未排期分组、统计与分页一致；发起人缺失；补录拒绝录音/识别失败/歧义/重复提交；日报同步失败重试、重复事件、多任务洞察闭环、取消完成和锁定日报更正。沿用隔离测试数据，不重置本地或云端用户数据。
