# 标书解析 · 架构与规则配置

把一个招标整包（RFP 正文、技术规范、合同、修订、澄清、报价清单、图纸……）解析成**拆标分解表**：每条要求归入「技术 / 交付 / 价格 / 商务 / 偏差」，标出强制 / 否决强度、风险和出处，按责任分工给出负责、复核角色和倒排截止日。口径来自《投标流程-方案与待办》第二章「标书分解」。

入口：
- **解析**在投标详情的「招标文件」Tab（P9.4）：上传整包（文件 / 文件夹）或从样本库选择 → 跑流水线 → 文件角色、关键字段、修订引用、拆标分解表。要求按「类别 + 文件」合并成拆标分解条目写回投标（`bid_item`，node 3 标书分解，带 `tenderKey` / `requirementIds`），重传新版按 `tenderKey` 只更新未开始的条目、不重复生成；点条目展开看它包含的原始要求，也可切到「按要求」逐条看。
- **规则配置**是独立页面：左侧栏「标书解析规则」（`/tender`），只放规则维护、试跑、历史版本与回滚，不和投标放在一起。

投标侧接口：`GET /api/bids/:id/tender`（最近一次解析 + 生成的条目 + 正在跑的任务）· `POST /api/bids/:id/tender/parse`（{sample}）· `POST /api/bids/:id/tender/upload`（multipart files[] + name）。后两个接口立即返回后台任务，进度查 `GET /api/tender/jobs/:id`；任务只在进程内跑，服务重启后会标为中断。

## 模型判断

配置了模型（`.env` 的 `MODEL_API_BASE_URL`、`MODEL_API_KEY`、`MODEL_NAME`）并在规则页启用时，第 4 步变成：规则放宽筛出候选（命中任一分类词、强度词、风险词）→ `tender/judge.ts` 分批调模型 → 校验 → `tender/merge.ts` 裁决。

- 校验：格式、条款编号必须属于本批、引用必须是该条款原文的连续片段（忽略空白和大小写）。没通过的条款重试一次，仍不通过就退回规则结果并标「待确认」。
- 护栏：规则判否决的不许模型单方面下调或排除，规则判高风险的不许模型单方面去掉。
- 标「待确认」：强制档分歧（一方判强制或否决，另一方没有）、护栏触发、置信度低于门槛、模型未复核。只有类别不同不标，详情里显示规则的判断作对照。
- 模型判定不是要求的条款不进分解表，存在 `tender_excluded/{runId}`。
- 连续 3 批调用失败就停止，其余条款用规则结果，并在结果里说明。
- 结论按「提示词 + 口径 + 示例 + 模型 + 条款正文」缓存在 `tender_judgments`，重传新版只重判变化的条款。
- 提示词、公司口径、标注示例和规则同一个版本，在规则页「模型判断」维护。条款原文只作为数据传给模型，不进系统指令。
- 没配模型时结果和原来一样，页面明确提示「未经模型复核」。

## 人工复核

在「招标文件」Tab 展开一条要求，可以确认无误、改类别和强度或判为不是要求；「已排除」列出没进分解表的条款（模型判定不是要求、规则没选中、人工排除），可以捞回。接口：`PATCH /api/bids/:id/tender/clauses/:clauseKey`、`GET /api/bids/:id/tender/excluded`。

- 只有主管和管理员能改判，其他人只读（方案 Q3 待确认）。解析进行中不能改判。
- 人的结论优先级最高，存在 `tender_feedback/{bidId}:{clauseKey}`，重传新版后按 `clauseKey` 继续生效；多次改判时 `before` 保留机器最初的判断。
- 改判后重算统计，并同步 `bid_item`。换类别时负责、复核和截止按责任分工重算。已开始的条目不动；未开始的条目要求全被改走时清零并从列表隐藏，不删除。

标注与回放：`npx tsx scripts/tender-gold.ts sample [每包条数]` 抽样到 `data/tender-gold.json`（Git 忽略，招标原文不进仓库），人工校对后 `npx tsx scripts/tender-gold.ts eval` 对比规则和模型的否决、强制召回和类别准确率。

## 流水线

| 步 | 做什么 | 代码 | 用到的规则 |
|---|---|---|---|
| 1 文件抽取 | PDF（pdfjs，按页）、DOCX（mammoth）、XLSX（每张表一页）、旧版 DOC（UTF-16 粗提取）、ZIP（展开一层）；PDF 每页字数低于门槛判为扫描页 | `apps/server/src/tender/extract.ts` | 解析参数 |
| 2 文件角色 | 文件名正则 +3 分、前两页关键词 +1 分，取最高分；角色带「效力顺序」和「是否拆条款」 | `pipeline.ts · classifyRole` | 文件角色识别 |
| 3 章节切分 | 标题正则切章节并取章节编号；章节内按列表项、句末标点切条款，过短合并、过长按句切 | `pipeline.ts · segment` | 章节标题、解析参数 |
| 4 条款打标 | 五类关键词打分（章节标题也计分）、强制项强度（禁止 > 强制 > 建议）、风险命中 | `pipeline.ts · tagClause` | 拆标分类、强制项判定、风险提示 |
| 5 包级汇总 | 关键字段多文件取值（采用效力最高的值，标「已被修订 / 待核对」）；修订 / 澄清文件里的条款号回指原章节；生成拆标分解表并倒排截止 | `pipeline.ts · parsePackage` | 关键字段、责任分工 |

进分解表的条件：带风险的条款；或强度为强制 / 禁止且分类得分 ≥ 下限；或澄清文件里分类得分 ≥ 下限的条款。单包最多保留 1500 条（超出按风险等级、强度、文件效力排序截断，并在结果里提示）。

## 规则配置

- 规则存 `documents` 表：`tender_rules/active` 为当前版本，`tender_rules_history/v{n}` 为每次保存的快照。
- 保存带乐观锁（提交的 version 必须等于当前版本），正则逐条校验，字段正则必须有捕获组。
- 「试跑」用页面上未保存的规则对一段原文跑第 3–5 步，不落库，方便边改边看。
- 「恢复默认」回到 `default-rules.ts` 的出厂规则；「历史版本」可回滚到任一版本（回滚本身也生成新版本）。
- 只有 manager / admin 能保存（方案 Q3「拆解规则由谁维护」待确认，先按主管 / BSD 口径）；所有人都能解析和试跑。

## 接口

```
GET  /api/tender/rules              当前规则 + 是否可编辑
PUT  /api/tender/rules              保存（body 为整套规则，带 version）
POST /api/tender/rules/reset        恢复默认
GET  /api/tender/rules/history      版本列表
POST /api/tender/rules/restore      {version} 回滚
POST /api/tender/rules/preview      {text, rules?} 试跑
GET  /api/tender/samples            样本目录（默认 ../招标文件样本，TENDER_SAMPLE_DIR 可改）
POST /api/tender/parse              {sample} 解析样本
POST /api/tender/upload             multipart files[] + name，上传整包解析
GET  /api/tender/runs[/:id]         解析记录
```

## 真实整包里遇到的问题（2026-11-11，Bungaban BESS RFP，27 个文件）

| 问题 | 处理 |
|---|---|
| 1100 万字的气温原始数据表让切分卡死（整包超过 10 分钟） | 没有句末标点的长段及时切断；工作表 XML 超过 1 MB 只读开头；纯数字行跳过。整包降到约 10 秒 |
| 附件既有文件夹又有同内容的 `Appendices.zip`，22 个文件重复 | 按文件内容去重，先解析包外文件 |
| 文件夹名（「A.2 SLD」「A.5 … GA」「Appendix B - Returnable Schedules」）没参与角色判断；`o&?m`、`form`、`format` 等短词误中「Comms」「OSOM」「Information」 | 文件夹名命中 +2 分；短词加词边界；新增「应答表 / 回传资料」角色（要拆条款） |
| 「Closing Time: 5pm (AEST), Friday 16 th October 2026」认不出 | 截止时间关键词加 RFP / tender closing time，允许中间夹时刻，序数词前可有空格 |
| 关键字段按「规范 > 正文」取值，图纸里单个集装箱的 5.1 MWh 被当成项目容量 | 只从拆条款的文件取字段；修订 / 澄清优先，其余取出现最多的值；多个取值不再标「多处一致」 |
| Word 规范的自动编号标题在纯文本里丢失，整份规范只有 1 个章节 | docx 走 HTML，标题样式和列表项保留 |
| 「The Supplier must:」后的列表项单看没有情态词；「The Proposal must be submitted via Aconex」没命中分类词被丢 | 列表项带上引导语；强制和否决不再要求分类得分，按文件性质给默认类别；目录行跳过 |

`npx tsx scripts/tender-smoke.ts [关键字]` 现在也会列出样本库根目录下的文件夹（不必放进「整包」）。

## 已知限制 / 后续

- 扫描件不做 OCR，只在结果里提示。
- `.QZZF` 等电子招标专用格式不支持，需要从交易平台导出 PDF。
- 还没有自进化：人工结论已经攒在 `tender_feedback`，但还不会自动变成示例或规则。
- 分解表还没有接到投标详情的「标书分解 → BSD 审核 → 派发待办」，接口 `/bids/:id/ai/decompose` 可改为读取这里的结果。
